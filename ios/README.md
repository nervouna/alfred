# iOS client

`AlfredKit/` is a Swift package with the client's Codable model of Alfred's API: events, commands and the objects they carry. Its tests decode the shared JSON fixtures in `fixtures/api/`.

`Alfred/` is the app, and `AlfredShare/` is its Share Extension. `Shared/` holds the code both compile: the keychain store, the 50 MiB limit, the HEIC-to-JPEG conversion, and the share logic (what the extension reads, `ShareModel`), which lives there so the app's unit tests can reach it. `Config/` holds the build settings. `project.yml` is the XcodeGen spec for the Xcode project; the `.xcodeproj` is generated and not committed.

Build tools: Xcode 27 and XcodeGen (`brew install xcodegen`).

## The app

The 对话 tab is the chat with Alfred, 任务 lists the owner's tasks and Alfred's recent runs, and 文档 lists the documents it delivered, each with its versions, and the owner annotates them there. Any file opens in the viewer.

- `App/` holds `AppModel`, which owns the credentials, the event stream and the `Timeline` it builds, and the owner's sends. The views only read it, and reach it through the SwiftUI environment (`RootView` puts it there).
- `Pairing/` is the first screen, shown while the app has no credentials.
- `Chat/` is the conversation: messages in timeline order (messages from the retired WeChat channel, still in the event log, tagged `微信`, and its failed sends `微信未送达`) with Alfred's questions as cards where they were asked, the owner's pending messages dimmed until their echo arrives (a failed send says `发送失败，点按重试` and a tap sends it again with the same `clientId`), each chat run's draft reply with its latest step under it, the composer with its attach button, a stop button while a chat run runs (it stops that run only), and the header (`ChatHeader.swift`, see Avatar below): a placeholder button `占位` on the left, Alfred's avatar in the middle and a menu with `取消配对` on the right. A file chip under a message opens its file: the document's screen, at the version the message delivered, when the message's file names a document (see Documents below), and the viewer otherwise. A message that a task's run delivered carries the task's title as a small label above its bubble, when the app knows the task (see Tasks below). A scheduled task's run is not the chat's: its draft and steps stay out of the chat, and the stop button does not stop it. While one runs, a row above the composer (`taskRunBanner`) says `定时任务「<title>」运行中`, with the run's latest step under it when there is one. The title is the task's when the app knows the task, else the run's. One row per run, oldest first; a tap opens the run's detail, the same view as in 任务, with its own `停止`.
- `Avatar/` is Alfred's avatar in the chat header: its state and the director that picks the next clip (`AvatarDirector`), the player (`AvatarPlayer`), the view (`AvatarView`) and the clips' folder (`Clips/`). See Avatar below.
- `Tasks/` is the 任务 tab, described under Tasks below. Below the tasks it lists the recent runs: the list is fetched (`GET /api/runs`) when the tab appears and on pull to refresh, newest first; a run the stream knows takes its latest version from the `Timeline`, so a running run updates live, and a run only the stream has told of is listed too.
- `Runs/` holds what shows a run, in that list and in a task's runs. A row shows the title, the status (排队中, 进行中, 完成, 已停止, 失败, 中断), `子任务` for a subagent, the short model name, the cost (`$0.003` under a dollar, `$1.25` from a dollar up) and the start time. A run's detail (`GET /api/runs/<id>`) shows its steps, the files it wrote, its error, a link to the parent run for a subagent, its document when it is a revision run (`documentId`), which opens the document's screen, and a `停止` button while it is running, which sends `run.stop`. The files list stays for the files a run wrote without delivering them.
- `Documents/` is the 文档 tab, a document's screen and the viewer, described under Documents and The viewer below. `AppModel` keeps the documents (`DocumentCatalog`), as it keeps the tasks.
- `Push/` is the notifications: the app delegate, what the app asks the system for, the token and the payload. See Push below.
- `AppIcon.icon` is the app icon, an Icon Composer document with two image layers and the system glass off: the dinner suit and bow tie, cut out, over an oxblood plate. The dark appearance swaps in a darker plate; the clear and tinted appearances hide the plate and let the system tint the suit.

### Tasks

The 任务 tab lists the owner's tasks above the recent runs (`Tasks/`). A task is a brief Alfred runs on a schedule; the app creates, changes and runs tasks with the task commands, and `AppModel` keeps them (`TaskCatalog`).

- **The list.** Active and paused tasks come first, newest created first, a paused one marked `已暂停`; tasks that have ended are under a collapsed `已结束`. A row shows the title, the schedule in words and the next run as a relative time. With no tasks the tab shows only the runs. The `+` button opens the form.
- **Schedules in words.** `每天 08:00`, `每周一、三、五 08:00` (`每个工作日 08:00` for Monday to Friday, `每天 08:00` for all seven days), `每 6 小时` and `10月28日 09:00 一次`. A time of day and the weekdays are in the owner's zone (`TaskList.timeZone`, not the phone's); when the phone's clock reads differently (another UTC offset), they say whose time it is: `每天 08:00（台北时间）`. A one-time run is an instant and shows on the phone's clock.
- **Kept current.** `AppModel` reads `GET /api/tasks` when the stream connects (and again each time it reconnects), when the tab appears and on pull to refresh, and applies every `task.updated` event. A task takes its latest version by `updatedAt`, so a list read before an event cannot undo it, and tasks are never removed. A task that ends moves to `已结束`.
- **The detail** (`GET /api/tasks/<id>`) shows the brief in full, the schedule in words, the next run (date and relative), the model, the per-run cap, the origin (`手动`, `对话`, `想法`), the skips with their time and reason (`错过（Alfred 当时未运行）`, `已达每日上限`) and the task's runs, each opening the run's detail. The task follows `task.updated` and its runs follow `run.updated`. The actions: `编辑`, `暂停` for an active task or `恢复` for a paused or an ended one (which makes it active again), `立即运行` (`已排队` shows until the run appears among the runs) and `结束`, which asks first. A refusal from the server shows as its own message.
- **The form** creates a task and edits one: title, brief, 每天 / 每周 / 每隔 / 一次 with a time picker (on the owner's clock), weekday toggles, an hours stepper from 1 to 168 or a date-and-time picker, the model (sonnet by default) and the per-run cap in USD (2 by default, at most 20). It checks what the contract checks before it sends: a blank title or brief, no weekday, a one-time run in the past (only when the schedule is new or changed), a cap outside 0 to 20. Creating sends the form's fields; editing sends only the fields that changed, and nothing when none did. A 400 shows its message at the top of the form and keeps what was typed.

### Documents

A file Alfred delivers is a document, known by its workspace path; delivering the same path again adds a version (`Documents/`). The 文档 tab lists the owner's documents, `AppModel` keeps them (`DocumentCatalog`), and the viewer shows any version of one.

- **Kept current.** `AppModel` reads `GET /api/documents` when the tab appears and on pull to refresh, and applies every `document.updated` event. A document takes its latest version by `updatedAt`, so a list read before an event cannot undo it, and documents are never removed. The catalog also keeps the `annotation.updated` events per document; nothing shows them yet. It is cleared on unpairing.
- **The list.** Newest `updatedAt` first. A row shows the title, the symbol of its kind (the viewer's, by extension), the folder (`工作区` at the top), the date and, when the document has a task the app knows, the task's name. Files a run wrote without delivering are not documents; they stay in that run's detail.
- **A document's screen** (`DocumentScreen`) loads `GET /api/documents/<id>` and shows the current version in the viewer of its kind. A toolbar button, `版本`, opens the list of versions, newest first: `第 3 版`, `当前` on the newest, what made it (`交付`, `修订`, `撤销`, `修改`), when (relative, like run times) and the run id when there is one. Tapping a version opens it read-only, under a banner that says which version it is (`正在查看第 1 版（交付）`) with a button back to the current one (`回到当前版本`). The screen loads the detail again when the stream says the document has a new version, and follows the current version while it is on it.
- **Changed blocks.** A Markdown version that has a version before it marks the blocks that changed or were added since it with a bar at the leading edge, in the accent colour, which VoiceOver reads as `已修改`. Blocks are compared by the text `MarkdownDocument` reads from them (with their kind: a table's text is its cells, and a paragraph made a heading has changed), matched with a longest common subsequence (`MarkdownChanges`). A removed block marks nothing, and a block that moved is marked at its new place. The first version marks nothing, and neither do other kinds. The older version is fetched like any other, and a failed fetch shows the version without marks and says so.
- **From a message.** A file of Alfred's message that names a document (`FileRef.documentId` and `.version`) opens the document's screen at the version the message delivered. When the document's current version is another one, a banner says `有更新的版本` with a button that opens the current version (`查看最新版本`). A file with no document (older messages, the owner's uploads) opens in the viewer as before.
- **Tasks and runs.** A task's detail lists the documents with its `taskId`, newest first, each opening its screen. A run's detail shows its document when `documentId` is set.

### Annotating

The owner annotates a document on the phone and hands the annotations to Alfred. A comment is a draft until 提交 sends the drafts as one batch, and Alfred revises the document in a run of its own (see Documents in the main README).

- **Selecting.** On the current version of a Markdown or text document, selecting text within one block (a paragraph, heading, list item, quote, code block or table cell; the whole text for a text document) offers `批注` first in the edit menu, beside the system's actions. A sheet shows the selected text and a comment field; `保存` keeps a draft. Older versions are read-only: no `批注` there, and no `整篇批注`. A selection cannot cross from one block to the next. The sheet refuses a quote or a comment over 2000 characters, which is Alfred's limit.
- **Whole document.** `整篇批注` in the toolbar opens the same sheet with no quote, on every document: HTML, PDF and images take it too. Passages in HTML and PDF, and PDF pages, are not annotated yet (#120).
- **How the selection is read.** Each run of text of a Markdown document, and a text document as a whole, is a UIKit text view (`PassageText`, `PassageTextView`) set the way the SwiftUI `Text` it replaced was. Its delegate's `editMenuForTextIn` gives the range of the selection and adds `批注` to the menu, and `AnchorText` turns that range into a target. A container view (`PassageTextContainer`) keeps the text view out of the accessibility tree and offers the text as one static text, and each highlight as a button.
- **The text a passage anchors on.** For Markdown, the plain text of the blocks `MarkdownDocument` reads, joined with `\n`, with a table's cells each a block of their own; for a text document, the file's text (the part the viewer shows, 256 KB at most). A passage target holds the selected text as `quote`, and up to 32 characters (Unicode scalars, as Alfred counts them) of that text before and after it as `prefix` and `suffix`. `AnchorText.locate` anchors a target on a version's text: every occurrence of the quote inside one block, ranked by how much of the prefix ends right before it plus how much of the suffix starts right after it; the best wins and a tie goes to the first. A quote that does not occur, or only occurs across a block boundary, does not fit.
- **Drafts** are kept per document in `Application Support/Alfred/annotation-drafts.json`, written atomically at every change, with the version each was written on. They survive a relaunch, and are cleared and the file deleted when the app unpairs or pairs again. A draft can be edited (its words) and deleted. When the current version of a document is shown, a draft written on an older version is anchored on it: a whole-document comment takes the version, a passage that fits takes the context it has there, and one that does not stays as it was, and is listed as 已失配.
- **Highlights.** On the version shown, drafts and `submitted` annotations that fit are tinted over their words, a draft yellow and a submitted one blue; VoiceOver reads them as buttons named `草稿` and `修订中`. A tap opens the card: the quote, the comment, the state, Alfred's reply when there is one, and for a draft `编辑` and `删除`.
- **The 批注 list** is behind the toolbar button with the number of drafts and annotations still with Alfred. Its sections, the empty ones left out: `草稿`, `修订中` (`submitted`), `已回复` (`resolved`, with Alfred's reply), `已退回` (`returned`, with its reason: `未回复`, `已撤销`, `已停止` or `失败`) and `已失配` (drafts and submitted passages that do not fit the version shown, with their quote). `重新编辑` on a returned annotation makes a draft from it on the current version (a passage is anchored again, and lands in `已失配` if it no longer fits); it is not offered while a draft made from that annotation exists. A draft in `已失配` can become a comment on the whole document (`改为整篇批注`) or be deleted.
- **Submitting.** With drafts on the current version, `提交 N 条批注` sends the ones that will go (the whole-document comments, and the passages that fit; at most 50) as one `document.revise` on the current version, in the order they were written, each passage with the context it has in that version. On 202 those drafts are removed and the annotations Alfred recorded show as `submitted` at once. On 409 the document's detail is read again, the drafts stay and are anchored again on the new version, and the server's message is shown; on 400, any other refusal or a network error the drafts stay and the message is shown.
- **While Alfred revises.** A banner, `排队修订中` or `Alfred 正在修订`, shows while a revision run of the document is queued or running (the detail's runs, kept current by `run.updated` events), with `停止`, which sends `run.stop`. When the run ends the screen loads the document again: the new version, the replies and the annotations that went back. A screen that a message opened stays on the version that message delivered, under its `有更新的版本` notice.
- **Undo.** When the document's current version is a `revised` one, a menu in the toolbar offers `撤销这次修订`, behind a confirmation that names the version's time. It sends `document.undo` with the run that made the version; on success the document is loaded again at its new `undone` version, and a 409 shows the server's message.

### The viewer

A file is downloaded (`GET /api/files/<path>`, with `?version=` for a version, to a temporary file that goes with the screen) and shown by the extension of its name. Downloads are kept by path and version, so two versions never share a file and a version the screen comes back to is not fetched again; the live file (no version) is fetched each time:

| Extension | Viewer |
|---|---|
| `md`, `markdown` | Markdown, block by block |
| `pdf` | PDFKit |
| `png`, `jpg`, `jpeg`, `gif`, `webp`, `heic` | the image, zoomable |
| `txt`, `json`, `jsonl`, `csv`, `tsv`, `log`, `yaml`, `yml`, `xml`, `js`, `ts`, `py`, `sh`, `css` | monospaced text (the first 256 KB) |
| `html`, `htm`, `svg` | the isolated web view |
| anything else | QuickLook |

Every viewer has a share button for the downloaded file. A failed download shows its reason and a retry.

Markdown is read with `AttributedString(markdown:)` and its full syntax. Each run of text says which blocks it is in (its presentation intent), and consecutive runs of the same innermost block become one block: headings, paragraphs, list items (with their bullet or number and nesting), block quotes, code blocks, thematic breaks and tables. Each block's text is a UIKit text view, so a selection can be read (see Annotating). Images show as their alt text, nothing loads, and only a web link opens, in the system browser.

An HTML report runs in a web view that is kept away from the app, as the workbench's `REPORT_CSP` does for the web: its own script and style run so charts draw, and nothing loads from anywhere.

- The web view uses a non-persistent website data store and has no script message handler, so the page cannot call into the app, and the app's tokens (the keychain and `AlfredClient`) are out of its reach.
- A content rule list blocks every load but the document itself and `data:` URLs. The web view does not load until the list is compiled, and a report whose list cannot be compiled is not shown.
- The report loads from a string with a `nil` base URL. The navigation delegate allows that one load and cancels every navigation after it, so a tapped link, a form or a script that sets the location opens nothing, and link previews are off.

### Pairing

One QR code carries the server URL, the Cloudflare Access service token and the device token. The app pairs in one of two ways:

- **Scan the QR code.** The scanner (VisionKit's `DataScannerViewController`) is offered where the device has a camera and the camera is allowed. The simulator has none.
- **Paste the pairing.** Copy the pairing JSON, then tap the paste button (`粘贴配对信息`). It needs no paste prompt, and it is the way in on the simulator and in UI tests. The JSON may come after other text, so the whole `[pairing] {…}` line `app-dev` prints can be pasted.

The app decodes the pairing, checks it with `GET /api/ping`, and only then saves it to the keychain. A failure stays on the screen with its reason: not a valid pairing, the device was refused (401), Access refused (403), or a network error.

The credentials live in one keychain item (service `alfred`), in the access group from the `AlfredKeychainAccessGroup` Info.plist value (`$(AppIdentifierPrefix)$(ALFRED_BUNDLE_ID)`). The Share Extension has the same key in its own Info.plist and the same group in its entitlements, and reads the item through `AppKeychain` too. A simulator build has no group, so both use their default one; signed the same way, they get the same default, and the extension reads the pairing in the simulator as well (`ShareUITests` relies on it). The simulator's keychain refuses an app that is not signed (status -34018): build the simulator app with the default signing, as the test commands below do, and not with `CODE_SIGNING_ALLOWED=NO`, which is only good for checking that it compiles.

If the server stops accepting the device, the app says so and offers `重新配对`, which deletes the credentials. If Cloudflare Access refuses the stream, it offers a retry. `取消配对` in the chat's menu deletes the credentials too, after a confirmation.

### The event stream

The app follows `/api/events` from the `Timeline`'s last event id while its scene is active. A scene that goes to the background drops the stream; when it is active again, the stream starts from the same id, so what happened meanwhile arrives then. A banner says `连接中…` until the stream is connected. Each time it connects the app also reads the task list again.

### Attachments

The `+` button in the composer offers 照片 (the system photo picker, several at once) and 文件 (the file picker, any type). A chosen item is copied into the app's temporary `attachments/` area and shows as a removable chip above the field; the copy goes when the chip is removed, when the message's echo arrives, or when the app unpairs.

- **Limits.** At most 10 files, each at most 50 MiB (Alfred's own limits). A file over the limit, or one past the tenth, is refused with its name in an alert; the others are still added. A file over the limit is refused before it is copied.
- **Photos.** Claude reads JPEG, PNG, GIF and WebP, not HEIC. A photo in any other format (HEIC, HEIF, TIFF, RAW) is written as a JPEG with ImageIO (quality 0.9, orientation and metadata kept) and uploaded as `<name>.jpg`; a photo already in one of the four formats goes up as it is. A file picked with 文件 is never converted.
- **Sending.** The message shows as pending at once, with a chip per file. The files are uploaded one after the other in the order they were chosen (`POST /api/uploads`, streamed from the staged copy), each chip showing its progress; when every file is saved, `message.send` goes out with their `FileRef`s and the text, which may be empty. A file that fails to upload is marked `上传失败` and the others still go up, but the message is not sent; the pending message says `发送失败，点按重试`, and the retry uploads only the files that failed (a file already saved is not uploaded again) before it sends, with the same `clientId`.

### Questions

A `question.asked` event shows as a card where it was asked, in event order among the messages: each question's header and text, and its options with their descriptions. `Timeline` keeps every question with its state and its position (how many messages came before it), so the card stays where it was asked.

- **Answering.** With one question that is not multi-select, tapping an option sends `question.answer` at once. Otherwise the options toggle and `提交` sends all the answers, with the labels of a multi-select question joined by `, `. Typing in the composer answers an open question too, but that is the server's rule and the card says nothing about it. A failed answer shows an error on the card and leaves the question open.
- **Afterwards.** An answered question shows its answers. A question cancelled by a stop shows `已取消`. A question whose run ended (`done`, `stopped`, `failed` or `lost`) without an answer shows `已结束`: the `Timeline` closes it on that `run.updated`.

### Avatar

The 对话 tab draws its own header (`Chat/ChatHeader.swift`) in place of the system navigation bar, which is hidden on this screen only; the title `对话` stays, as the name of the back button on the screens the chat opens. The header is a `safeAreaBar` under the status bar and the Dynamic Island that holds the two buttons and nothing else (identifier `chat.header.bar`, an element with the bar's frame): a round glass button on each side (44 pt tap target, the system's glass), the placeholder `占位` (symbol `circle.dashed`, no action yet, a slot for a later feature, identifier `chat.header.leading`) and the 更多 menu with `取消配对` (`chat.header.menu`). The bar is exactly as tall as the system's inline navigation bar: its height is what UIKit gives a navigation bar of its own on the device (`SystemBar.inlineHeight`, 54 pt on an iPhone 17 in iOS 27), not a number of ours, so the bar's background (its scrim) and hit area end where a system bar's would. In the middle is the avatar (`chat.header.avatar`), a 72 pt circle with a thin ring, 1.6 times the buttons. It is not part of the bar: it is drawn by `ChatHeaderOverlay`, an overlay of the chat above the bar and the list. The overlay is laid out in the safe area, so the avatar's top is 48 pt above the bar's bottom edge (`ChatHeader.avatarOffset` below the bar's top) and its lower third, 24 pt (`AvatarMetrics.hang`), hangs below the bar over the messages. It takes no touches, so a drag that starts on it scrolls the list. The list keeps those 24 pt of `contentMargins` above its first message: at rest nothing is hidden, and messages scroll under the avatar. While `连接中…` shows, a small capsule on the bar's material (`.bar`) with the spinner and the text sits centred just below the avatar, floating over the list; it is part of the overlay too, so the bar does not change. The bar has no material: the list's scroll edge effect is hidden at its top (`scrollEdgeEffectHidden(true, for: .top)`), and behind the bar a scrim (`ChatHeaderScrim`) of `Color(.systemBackground)` runs from the screen's top edge to the bar's bottom edge, 50% opaque at the top and clear at the bottom (`ChatHeader.scrimTopOpacity` and `scrimBottomOpacity`), so messages scrolling under it stay visible.

- **States.** `AvatarState` is `working` while `AppModel.runningChatRun` is not nil, and `standingBy` otherwise. A scheduled task's run is not the chat's and does not count.
- **The director** (`AvatarDirector`, pure: no SwiftUI or AVFoundation; it takes a random source and a clock) answers with a cue, a clip and the time to start it, when it is started, when the state changes and when a clip ends. Standing by, it cues `blink` (weight 3), `smile` (1) or `yawn` (1) after a pause of 8 to 20 seconds, over and over, never the same clip twice in a row (the clip that just played is left out of the draw, and the others keep their weights). When the state turns to `working`, the clip in progress finishes and `workStart` follows, or `workStart` comes at once when it is in a pause; then `workLoop` repeats for as long as the state is `working`. When it turns back to `standingBy`, the pass of `workLoop` in progress finishes, then `workEnd` plays, then the idle cycle starts again with a pause (a flip during `workStart` goes straight to `workEnd`). A flip back to `working` while `workEnd` plays lets `workEnd` finish, and `workStart` follows. With Reduce Motion on there are no clips at all, only the still.
- **The clips** are bundle resources in `Alfred/Avatar/Clips/`: `blink.mp4`, `smile.mp4`, `yawn.mp4`, `work-start.mp4`, `work-loop.mp4` and `work-end.mp4`, and the pictures of the two poses, `still.png` (the standing pose, the resting picture) and `typing.png` (the typing pose, the first frame of `work-loop`; both 360×360). Each clip is square, H.264 in an `.mp4`, with no audio track, 24 fps and 4 seconds at most (`work-loop`, which repeats, may run longer). `blink`, `smile`, `yawn` and `work-end` end on the resting pose, which `still.png` shows; `blink`, `smile`, `yawn` and `work-start` start on it. `work-start` ends on the typing pose; `work-loop` starts and ends on it, so that it repeats without a seam; `work-end` starts on it. A clip is shown as soon as it is in the folder: `xcodegen generate` copies every file there into the app bundle's top level as a resource (and not the `.gitkeep`), so no change to `project.yml` is needed.
- **The player** (`AvatarPlayer`) plays one clip at a time, muted, drawn through two `AVPlayerLayer`s in one view (`AvatarPlayerSurface`), one `AVPlayer` for each (`AvatarLane`). The clips have no audio track and the app never touches the audio session, so other apps' audio plays on. Playback stops while the app is not active (and while the chat is off the screen); when it is back the cycle starts again from the still.
- **No gap between clips.** A player that is given a new item draws nothing until the item's first frame is ready, and the still under it shows through for a frame: measured on the simulator it was 26 ms. So a clip plays on the player that is not on screen, with its layer on top, and the clip that ended stays where it is: its last frame is the picture until the layer's `isReadyForDisplay` says that the new clip has its first, and only then is the old one taken off its player, in the same commit. A lane's layer is on screen only while it has a frame: it is transparent (opacity 0) from the start, goes on screen in that same commit once `isReadyForDisplay` is true, and goes off screen when its lane is cleared, so a clip that starts from rest never puts an empty layer over the picture under the video (from rest to a clip and from a clip back to rest the circle shows the picture or a drawn frame, at every sample). At no moment is there no frame (a clip whose first frame never comes, because the layer is not on a screen, takes over after one second). This needs no look-ahead, which the director cannot give: it decides what follows only when the clip ends (a pause, a flip of the state), so an `AVQueuePlayer` would have to be fed the next item after the clip ended, and measured that way it still left 11 ms; an `AVPlayerLooper` would cover `work-loop` to `work-loop` and not `work-start` to `work-loop` or `work-loop` to `work-end`.
- **The picture under the video** is the pose the clip starts on while it plays: `still.png` under `blink`, `smile`, `yawn` and `work-start` and while resting, `typing.png` under `work-loop` and `work-end` (`AvatarClip.startPose`). When a clip has ended, it is the pose the clip ended on (`endPose`): the still after `blink`, `smile`, `yawn` and `work-end`, the typing pose after `work-start` and `work-loop`. A rest, a stop and Reduce Motion show the still. The picture shows only where the video does not: before the first clip, after a rest, for a clip that cannot play, and for the time the next clip needs to draw.
- **Fallbacks.** The picture is the clip; without it (the file is missing, or AVFoundation cannot play it) the picture of the pose it starts on; a missing `typing.png` (or one that is not an image) is the still, and a missing still (or one that is not an image) a navy circle with the symbol `person.fill`. None of this is an error. A clip that cannot play is stood in for by a fixed 2 seconds, and then the director goes on as if it had played. With no files at all the avatar is the placeholder circle.

### Push

The workbench pushes through APNs for Alfred's outbound messages on the app channel, and for questions (`src/workbench/push.ts`). The payload is `aps.alert` (title `Alfred` and the text), `sound: default` and `thread-id: chat`, plus the custom keys `eventId` and, when there is one, `runId`.

- **Permission and token.** After a successful pairing, and at each launch while paired, the app asks the system for permission to show alerts, play sounds and badge the icon (the system asks the owner once), and registers for remote notifications. The token goes to `POST /api/push` as lowercase hex, with the environment from the Info.plist key `AlfredAPNsEnvironment`, which `project.yml` sets to `development`: the owner installs a Release build signed with a development profile, whose `aps-environment` entitlement (`Alfred.entitlements`) is `development`. A build without the key registers nothing.
- **Registering again.** A token Alfred accepted is not sent again until it changes or the app pairs again. A 401 or 403 is the pairing and access-error flow's to show; any other failure leaves the token unregistered, and the next launch sends it again.
- **In the foreground.** With the chat tab on screen (the app active, paired and without an access error) a notification is not shown, because the chat already has the message. On the other tabs it shows as a banner with sound. In the background the system shows it.
- **A tap.** It opens the chat tab and scrolls to the message or question card that `eventId` names, when the timeline has it (`AppModel` keeps the event id of each); otherwise the chat just opens. The tap makes a new list, and a scroll made while it is still laying out its first rows can land on an estimate or be undone by the list's own start at the bottom, so the request stays until the row has been on screen at two checks in a row: the chat scrolls to it again every 100 ms, up to 40 times. New events do not move the list meanwhile, and follow the bottom again afterwards.
- **Unpairing** calls `unregisterForRemoteNotifications`. The server keeps the registration until the device is revoked: it has no call to remove one.

To see how the app handles a notification, push a payload shaped like the server's to the simulator while the app is in the background:

```bash
cat > payload.json <<'EOF'
{"aps":{"alert":{"title":"Alfred","body":"报告写好了"},"sound":"default","thread-id":"chat"},"eventId":42,"runId":"k7m2qa"}
EOF
xcrun simctl push <udid> com.example.alfred payload.json
```

The simulator asks for notification permission the first time the app pairs; allow it. `PushUITests` does this whole check (see Test).

### Share Extension

Share one web page, PDF or image from any app (the activation rule in `project.yml` lets exactly one through). A small sheet shows what is shared, a note field and `发送`. Without credentials it says `请先在 Alfred 里完成配对` and offers `关闭`. `ShareModel` (in `Shared/`) holds the logic, and `SharedContentLoader` reads what the host app handed over.

- **A page** is one `message.send`: the note, a blank line, then the page's title (when the host gave one, cut to 300 characters) and the address. Only `http` and `https` addresses are pages.
- **A PDF or an image** is copied by the file system into the extension's scratch area (never read into memory, because an extension has little of it) and uploaded from there with `upload(fileAt:)`; then a `message.send` names the file and carries the note, which may be empty. An image in a format Claude cannot read, HEIC among them, is written as a JPEG by ImageIO straight from the system's file. A file over 50 MiB is refused before it is copied. The file is named as the host app names it, with the extension of the copy.
- **Sending** shows progress. On success the request completes. On a failure the sheet shows the reason and `重试`: a file that was saved is not uploaded again, and the message keeps its client id, so one that did arrive is not stored twice.

## Run against a local Alfred

`node scripts/app-dev.ts` (from the repository root) runs Alfred for the simulator: the real handler behind the command API, and the workbench on `http://127.0.0.1:8787` with no TLS. Point `ALFRED_STATE_DIR` and `ALFRED_WORKSPACE` at new scratch directories and set `ALFRED_ANTHROPIC_API_KEY`. Keep the state directory path short: the command API's Unix socket path has to fit in about 104 bytes, so use something like `mktemp -d /tmp/a.XXXX`. It prints the pairing as one `[pairing]` line: paste its JSON into the app. A later start says the simulator is already paired; `--repair` pairs a new device. `--seed-documents` writes two documents before Alfred starts, for the 文档 tab and `DocumentsUITests`: `reports/weekly.md`, a Markdown report with three versions (delivered, then revised with one paragraph changed and one added, then changed in a heading), and `reports/overview.html` with one; each version is committed with `Versions` and registered with `DocumentStore`. A document that is already registered is left alone, so a restarted stack keeps what it has. It then opens the workspace's history and the document store with `startDocuments` and passes them to the handler and the command API (`documentCommands`, with the documents, which turns undo on), as `node src/cli.ts run` does, so files Alfred delivers become documents and the app's revisions and undos run; the seeded documents were delivered by no run on record, so their revisions run on sonnet, and a document Alfred delivers in a chat on haiku is revised on haiku. Messages other than commands run the model (haiku, about a tenth of a cent each); `/status` costs nothing.

## Build for the phone

The owner's signing settings are not in the repo. Copy `Config/Signing.example.xcconfig` to `Config/Signing.xcconfig` (git ignores it) and fill in the team id and bundle id. `Base.xcconfig` includes that file, so the settings apply to every configuration.

```bash
xcodegen generate --spec ios/project.yml
```

The first install needs the developer trusted on the phone, under Settings > General > VPN & Device Management. Reinstall the app when its development profile expires.

## Test

Run the AlfredKit tests on macOS with Swift 6.0 or later: `swift test --package-path ios/AlfredKit`.

The app has two test targets in the `Alfred` scheme. Use a simulator of your own; `xcrun simctl create "alfred-test" com.apple.CoreSimulator.SimDeviceType.iPhone-18-Pro com.apple.CoreSimulator.SimRuntime.iOS-27-0` prints its id, and `xcrun simctl delete <id>` removes it. Build with the default signing (see Pairing), and add `-collect-test-diagnostics never` so a failed run does not wait on simulator diagnostics.

- `AlfredTests` are unit tests of `AppModel` on a stubbed `URLSession`: pairing, unpairing, sending and retrying, the stream's restart and its errors, attachments (the limits, the upload order, a failed upload and its retry, photos becoming JPEGs) and answering questions. They also cover the runs list, the documents (the catalog and the stream's events, the version labels and banner, where a message's file opens, the changed-block comparison, and the viewer's downloads kept by path and version), the tasks (the schedule in words with its zone note, the list's grouping and order, the form's checks and the fields it sends, `task.updated` events and the reload when the stream connects, the task commands, the chat label, the task run banner, and which run the stop button and the live replies take), the viewer chosen by extension, the Markdown blocks, the annotations (the anchor text and where a target fits: an exact quote, a repeated quote decided by its prefix and by its suffix, no match, a match across blocks, an empty prefix at the start; the draft store: saved, edited, deleted, kept across a reload, cleared on unpairing, anchored again on a newer version; the sections of the 批注 list for each state and return reason, the highlights, the banner from run states and the undo menu, which shows only on a `revised` current version; and the outcomes of a submission: 202, 409 with the detail read again, 400 and a network error), and the isolation of the report web view (the navigation policy, the rules, and a real `WKWebView` loading a page). `PushTests` covers the token as lowercase hex, the registration body and its environment, registering again, the access errors, the permission calls, the foreground rule, reading `eventId` and `runId` from the payload, and what a tap opens. `AvatarDirectorTests` runs the avatar's director on a seeded random source and a clock the test moves: only idle clips while standing by, each after a pause of 8 to 20 seconds, no clip twice in a row, the draws following the 3:1:1 weights (and 3:1 or 1:1 among the clips left when one is left out), `workStart` then only `workLoop`, a flip to standing by giving a last `workLoop` pass, `workEnd` and then the idle cycle, a flip back to working during `workEnd`, and no clip with Reduce Motion. `AvatarPlayerTests` covers the fallback chain in a folder of its own (no files, a still only, a still and a typing picture, a missing or unreadable `typing.png` standing in as the still, an unreadable clip with and without a still, a playable clip made on the spot), the stand-in for a clip that cannot play, and a clip played muted to its end. It also covers the underlay rule (which pose each clip starts and ends on, which picture is under each clip, which one shows after each clip ends, and that a rest or a stop shows the still) and the seams: with the avatar's surface in a window, a frame is on screen at every 1 ms sample from one clip to the next and the clip that ended leaves its player only once the next one has drawn (a single player that is given the next item fails both). `ChatHeaderTests` checks that the bar's height is the height of a real inline navigation bar (a UIKit one and a SwiftUI stack's, in a window), that the avatar's lower 24 pt are below the bar, and, with the real chat in a window in the dark appearance, that the avatar is 72 pt and its edges are where the bar's bottom edge puts them, whether or not `连接中…` shows; it does not judge the bar's edge effect, which a snapshot of a hosted view does not draw. `ShareTests` covers the extension's logic: no credentials, a page with a title and a note as one `message.send`, a PDF as an upload and then a `message.send` with the file, a HEIC image converted to a JPEG, a failed send and its retry, and `SharedContentLoader` on real `NSItemProvider`s.

  ```bash
  xcodegen generate --spec ios/project.yml
  xcodebuild test -project ios/Alfred.xcodeproj -scheme Alfred -destination 'id=<udid>' -derivedDataPath ios/build -only-testing:AlfredTests -collect-test-diagnostics never
  ```

- `AlfredUITests` drive the app against a running `app-dev`. Start `app-dev` as above, copy the JSON of its `[pairing]` line, and pass it as `TEST_RUNNER_ALFRED_PAIRING` (xcodebuild hands it to the test as `ALFRED_PAIRING`). `ChatUITests` puts the pairing on the pasteboard and taps the paste button, sends `/status` and a message the model answers, then goes to the home screen, sends a message from outside the app, and checks that it shows once the app is back; it also checks that the attach button offers 照片 and 文件. `RunsUITests` has Alfred write `notes/hi.md`, follows the run through the 任务 tab (完成), its detail and the viewer, and has Alfred `deliver` `notes/chip.md` and opens its file chip in the chat. Each test that runs the model costs about a tenth of a cent. Stop `app-dev` afterwards (SIGTERM, or Ctrl-C).

  ```bash
  TEST_RUNNER_ALFRED_PAIRING='{"version":1,…}' xcodebuild test -project ios/Alfred.xcodeproj -scheme Alfred -destination 'id=<udid>' -derivedDataPath ios/build -only-testing:AlfredUITests -collect-test-diagnostics never
  ```

  `QuestionsUITests` asks the model to put a question (red or blue) with `AskUserQuestion`, then answers it three ways in three tests: it taps an option on the question card and checks that the card shows the answer and that a reply names the color; it types an answer in the composer; it stops the run and checks that the card says `已取消`. Each test costs a fraction of a cent. The system photo and file pickers are not driven by the UI tests.

  `TasksUITests` works the 任务 tab. One test creates a task in the form (daily, haiku, a cap of $0.30, a brief that asks for a two-line note and no web access), finds it in the list, opens its detail (brief, schedule, model and cap), pauses it (`已暂停` shows in the detail and the list) and resumes it, taps `立即运行` and waits for a run of the task to finish among the detail's runs, checks that the chat shows a message labelled with the task's title, ends the task behind its confirmation and finds it under `已结束`. It runs the model once, on haiku, for a fraction of a cent. The other test runs nothing: it saves a blank form and checks that the form names the problems and stays open, creates a task, edits only its cap and checks the detail, and ends the task. Tasks stay on the stack, so each test looks for the task it made by a title with a number in it.

  `DocumentsUITests` runs against `node scripts/app-dev.ts --seed-documents` and no model. It checks that the 文档 tab lists both seeded documents, that the report opens at its third version (no banner) and that 版本 lists three versions with their labels (`修改`, `修订`, `交付`); it opens the first version and checks its banner, that nothing is marked, and the way back; and it checks that the second version has two marked blocks (`已修改`, beside the changed paragraph and the added one) and the third one. A last test opens the HTML report in the report viewer and finds one version.

  `AnnotationsUITests` runs against `node scripts/app-dev.ts --seed-documents`. The first test runs no model: it opens the seeded report, double-taps a word of a paragraph (which selects it and shows the edit menu, where `批注` is the first item), writes a comment and saves the draft, finds the highlight over the word and opens its card to edit the draft, adds a comment on the whole document, terminates and launches the app again, finds both drafts in the 批注 list and deletes one. The second test runs the model on haiku, for a few cents: Alfred writes and delivers a note in a chat run, so its revision runs on haiku too; the test opens the note from its file chip, annotates a word and the whole document, submits, sees the banner and waits for it to go, finds both replies under `已回复`, opens the revised version, undoes the revision behind its confirmation, and finds the batch under `已退回` with `已撤销`. Set `TEST_RUNNER_ALFRED_SHOTS` to a directory to have the tests save screenshots of the screens they pass through.

  `ChatHeaderUITests` runs against `node scripts/app-dev.ts` and no model. It checks that the header's two buttons (`chat.header.leading`, `占位`, and `chat.header.menu`, `更多`) and the avatar (`chat.header.avatar`) exist with their sizes (44 and 72 pt), the avatar centred between the buttons and hanging below them; that the bar (`chat.header.bar`) is as wide as the screen, holds the two buttons centred on it, is as tall as the system's inline navigation bar (read from the 新建任务 sheet on the 任务 tab, since the tab's own bar carries a large title; ±1 pt) and has the avatar's bottom edge 24 pt (±2) below its own; that the 更多 menu still offers `取消配对`; and, after eight `/status` replies and a scroll to the start of the chat, that the first message lies below the avatar and can be hit. That the bar keeps its height while `连接中…` shows is not checked there, since the test cannot make the stream disconnect; `ChatHeaderTests` covers it. With `TEST_RUNNER_ALFRED_SHOTS` set to a directory (xcodebuild hands it to the test as `ALFRED_SHOTS`), the last test saves screenshots of the chat at its start and a little further down, where messages pass under the bar, in the light and in the dark appearance (`chat-start-light.png`, `chat-start-dark.png`, `chat-under-bar-light.png`, `chat-under-bar-dark.png`), the way `AnnotationsUITests` saves its shots.

  `PushUITests` checks notifications end to end. A test in the simulator cannot call `xcrun simctl push`, so a loop outside it does: the test writes `ready-<n>` into the directory named by `TEST_RUNNER_ALFRED_PUSH_DIR` whenever it wants a push, and the loop pushes the `payload.json` the test wrote there. The test sends `/status` eight times so the first reply is far above the screen, and writes a payload that names that reply. With the chat on screen it checks that no banner shows; on the 任务 tab it checks that one does; with the app in the background it taps the banner and checks that the chat tab is selected and the first reply is on screen, three times, each from the 任务 tab. It answers the system's notification question with Allow; on a new simulator the question can come late, so the test looks for it twice.

  ```bash
  # shell 1: the test
  mkdir -p /tmp/push-check && rm -f /tmp/push-check/*
  TEST_RUNNER_ALFRED_PUSH_DIR=/tmp/push-check TEST_RUNNER_ALFRED_PAIRING='{"version":1,…}' xcodebuild test -project ios/Alfred.xcodeproj -scheme Alfred -destination 'id=<udid>' -derivedDataPath ios/build -only-testing:AlfredUITests/PushUITests -collect-test-diagnostics never
  # shell 2: pushes whenever the test asks, until it is done
  n=1; until [ -e /tmp/push-check/done ]; do if [ -e /tmp/push-check/ready-$n ]; then xcrun simctl push <udid> com.example.alfred /tmp/push-check/payload.json; n=$((n+1)); fi; sleep 0.5; done
  ```

  `ShareUITests` shares the newest photo of the simulator's library from the Photos app to Alfred, with a note, and checks that the message and its file arrive in the chat; a second test leaves the app unpaired and checks that the sheet says `请先在 Alfred 里完成配对` and closes with `关闭`. Add a photo first (`xcrun simctl addmedia <udid> <image>`). The extension is found by its name in the share sheet; Photos' own controls are found by their identifiers, which may change with the system.

  Without `ALFRED_PAIRING` the tests skip themselves, so a plain test run needs no stack. Each test starts from the pairing screen whatever the app was left in, so they can run again against the same stack or a new one. Server replies are waited for 30 s and model replies 120 s.

## Continuous integration

The `app` job in `.github/workflows/ios.yml` builds the simulator target on `macos-26`. No runner has Xcode 27 yet, so the job selects the newest installed Xcode and passes `IPHONEOS_DEPLOYMENT_TARGET` on the `xcodebuild` command line, set to that SDK's major version (26.0 for the Xcode 26 SDK). `project.yml` and local or device builds stay at iOS 27.0. Remove the override from the workflow once a runner has Xcode 27. CI only builds; it does not run the app's tests.
